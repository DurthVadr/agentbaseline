{{/* The page's own opening, not the homepage's line: what a factory is and what this architecture does about it. */}}

A software factory uses AI agents to turn a prompt, a ticket or a specification into tested code, and increasingly to deploy and operate it. Its agents decide what to do next and act on real systems, so this architecture keeps what an agent decides apart from what it is allowed to do. The agent proposes, policy authorizes, and infrastructure enforces.

Four boundaries

{{/* What the paper teaches first: the agent keeps its room to work, and what it can actually do is enforced outside its own decisions. */}}

An agent needs room to reason and try things. A secure factory gives it that room, and enforces what the agent can actually do from outside the agent’s own decisions. Four boundaries do the enforcing, and each one holds whether the agent cooperates or not.

{{ partial "software-factory-boundaries.html" $bd.boundaries }} {{ partial "sf-figure.html" (dict "n" $bd.figure.n "caption" $bd.figure.caption) }}
{{/* The paper's "A factory in action", cut to the moment that shows the separation, then the line that keeps tested code and the boundaries from reading as one thing (paper: the loops decide whether the software is acceptable, the boundaries what agents may do). */}}

Take an incident agent allowed to read one service’s logs for the last hour. If it decides it needs another service’s logs, the proxy blocks the request until a new authorization decision grants them. Tests are a separate question: the factory’s loops decide whether the software is good enough, and the boundaries decide what agents may do. Code can pass every test and still come from an agent that reached too far.

Three levels of autonomy

{{/* The paper's claim, plainly: who decides the next step changes; the boundaries don't. */}}

The three levels differ in who chooses the next step: a developer, a predefined workflow, or an agent. The four boundaries stay the same at every level. What grows is how much the infrastructure around them does that a person used to supervise.

Read the paper

{{/* Why to read the paper, not a list of its contents: it starts from what went wrong (Recent incidents: PocketOS; Hugging Face) and names the control each one was missing. */}}

The paper starts from real failures, including an agent that deleted a production database in nine seconds and another that got past the controls meant to contain it and tried to hide its tracks, and names the control each one was missing. It then shows what to build at each level of autonomy, and maps the architecture to Agent Baseline’s outcomes and controls.
